# 自动合成标签遍历 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 缺料自动合成遇到整合包配方标签时，不再按字母序把每个替代物递归搜到深度 8，从而避免一次 `plan()` 拖死服务端 tick。

**Architecture:** 只改 `VaultAutoCraftPlanner`。原料格先用库里已有的 id；都没有时，只递归「某条配方的每种原料都能在当前库存里对上」的 id，并优先 `minecraft:`。单次 `plan()` 最多 512 次 `ensure`，超限返回空计划（与现在的合不成一样，会被「同库内容记住失败」接住）。`countMatching` 在库存远小于标签时改为按库存键探测，避免排序时扫完整包标签。不改采购拆原料、不改虚拟单原料库存、不改每拍 2 次求解的外层预算。

**Tech Stack:** Java 17, Forge 1.20.1, JUnit 5 `unitTest`

### Task 2: 搜索策略与步数上限

**Files:**
- Modify: `src/main/java/com/touhoumaid/construction/build/VaultAutoCraftPlanner.java`

**Interfaces:**
- Consumes: Task 1 的三个测试
- Produces: `plan(...)` 签名不变。类内新增 `static final int MAX_VISITS = 512` 与私有 `SearchLimit`。`ensure` / `gatherIngredients` / `ensureAny` 增加最后一个参数 `SearchLimit limit`。

- [ ] **Step 1: 给 `plan` 装上步数上限**

在字段区增加：

```java
/** One plan() call. Stops tag explosions from pinning the server thread. */
static final int MAX_VISITS = 512;
```

`plan` 在调用 `ensure` 前创建 `SearchLimit limit = new SearchLimit(MAX_VISITS)`，并传进去。超限时 `ensure` 返回 false，`plan` 因此返回 `Optional.empty()`。

```java
private static final class SearchLimit {
    private int left;

    SearchLimit(int max) {
        this.left = max;
    }

    boolean take() {
        if (left <= 0) {
            return false;
        }
        left--;
        return true;
    }

    boolean alive() {
        return left > 0;
    }
}
```

`ensure` 在「库存已够则 return true」之后、查配方之前调用 `if (!limit.take()) return false;`。库存已够不消耗次数。

- [ ] **Step 2: `countMatching` 与空库排序**

`countMatching` 换成：库存空或列表空则 0。列表比库存大很多时，用库存键对 `HashSet` 探测，不要按标签逐个 `get`。

```java
private static int countMatching(Map<String, Integer> stock, List<String> itemIds) {
    if (stock == null || stock.isEmpty() || itemIds == null || itemIds.isEmpty()) {
        return 0;
    }
    if (itemIds.size() > 32 && itemIds.size() > stock.size() * 4) {
        java.util.Set<String> allowed = new java.util.HashSet<>(itemIds);
        int total = 0;
        for (Map.Entry<String, Integer> entry : stock.entrySet()) {
            Integer have = entry.getValue();
            if (have != null && have > 0 && allowed.contains(entry.getKey())) {
                total += have;
            }
        }
        return total;
    }
    int total = 0;
    for (String id : itemIds) {
        total += stock.getOrDefault(id, 0);
    }
    return total;
}
```

`ensure` 里给配方排序时：`stock.isEmpty()` 则只 `Comparator.comparing(VaultCraftRecipeView::id)`，不要调用 `readyIngredientSlots`。库存非空时保留现有「已齐原料槽优先，再比配方 id」，这样 `prefersDirectRecipeOverRecursive` 仍先用库里的木板。

- [ ] **Step 3: 重写 `ensureAny`，不要按字母序递归每个替代物**

保持开头：`countMatching >= need` 则 true。然后若 `!limit.alive()` 则 false。

若 `itemIds.size() == 1`：不要做可达性过滤，也不要因为库存里还没有这个 id 就返回。直接 `ensure` 这一个 id（受步数上限约束）。木棍 ← 木板 ← 原木这种单 id 链必须仍能递归。

仅当 `itemIds.size() > 1`（配方标签展开后的多个替代物）才继续。此时若 `stock.isEmpty()` 则直接 false，不要为了确认空库去查每个模组配方。否则把列表拷贝后按 `Comparator.naturalOrder()` 排序，再按顺序尝试，**某一组里第一个 `ensure` 成功且标签计数已够就返回**，不要继续扫同组剩下的：

1. 已在库存中（`stock.getOrDefault(id, 0) > 0`）且 id 以 `minecraft:` 开头。
2. 已在库存中的其它 id。
3. 不在库存中、id 以 `minecraft:` 开头、且 `reachableFromStock` 为 true。
4. 不在库存中的其它 id，且 `reachableFromStock` 为 true。

第 3、4 组在调用 `ensure` 之前先做 `reachableFromStock`。不可达的 id **不要** `ensure`，这样测试里的 `aether:` / `biomesoplenty:` 配方查询次数为 0。

`reachableFromStock`：该 id 已在库存中，或它的某条配方里**每一种**原料列表都与当前库存有交集（某种原料 id 的库存 > 0）。交集用与 `countMatching` 相同的「库存小就探库存键」判断，不要对大标签做嵌套全扫描。没有配方、或没有任何一条配方能被当前库存一步喂饱，返回 false。这一步允许调用 `recipesByResult`（原版木板那十几次查询是预期的）；禁止在这里递归 `ensure`。

伪代码：

```java
private static boolean ingredientHitsStock(Map<String, Integer> stock, List<String> itemIds) {
    return countMatching(stock, itemIds) > 0;
}

private static boolean reachableFromStock(
        Map<String, Integer> stock,
        String itemId,
        Function<String, List<VaultCraftRecipeView>> recipesByResult) {
    if (stock.getOrDefault(itemId, 0) > 0) {
        return true;
    }
    List<VaultCraftRecipeView> recipes = recipesByResult.apply(itemId);
    if (recipes == null) {
        return false;
    }
    for (VaultCraftRecipeView recipe : recipes) {
        if (recipe.ingredients() == null || recipe.ingredients().isEmpty()) {
            continue;
        }
        boolean allHit = true;
        for (VaultCraftRecipeView.Ingredient ingredient : recipe.ingredients()) {
            if (!ingredientHitsStock(stock, ingredient.itemIds())) {
                allHit = false;
                break;
            }
        }
        if (allHit) {
            return true;
        }
    }
    return false;
}
```

`tryEnsureId` 与采购规划器一样：拷贝 stock 与 steps，调用 `ensure`，成功才写回。失败的尝试不能污染调用方库存。

告示牌 / 台阶现有测试的原料是单一 id，不是大标签，仍走 `ensure` 递归（木棍 ← 木板 ← 木），不要用 `ensureAny` 的「一步可达」去截断这条链。`reachableFromStock` 只用于标签格选哪个 id。

## 不要做的事

- 不要把采购规划器的「商城能买就停」抄进自动合成。自动合成不能买，空库或库里对不上的标签必须失败，而不是去买原版木板。
- 不要提高 `MAX_ENSURES_PER_TICK`。那只限制一拍启动几次 `plan()`，挡不住一次 `plan()` 内部爆炸。
- 不要为了修这个去改配方索引（`Ingredient.getItems()` 展开标签是对的，问题在展开之后的搜索）。
- 不要 `git add -A`。施工队工作区里有大量无关未提交文件。
